# GPU 完整机制战斗推演（3.16.0 / P3）

P3 表示当前参考模拟器已实现的战斗机制均有 CUDA 执行路径，不代表全部游戏技能已实现、当前平衡准确或真实对局验收。预测规则配置与训练模型版本仍单独显示。

## 实际计算路径

默认 `prediction.gpu_combat=true`，启动时在所选 CUDA 设备编译并预热战斗内核；无 CUDA、缺依赖或内核失败时保留原 CPU 模拟。每个 GPU 线程推进一个完整独立战斗分支，不同卡牌、不同落点与不同敌情假设并行。单个分支保留原模拟的单位行动和弹道结算顺序，使用双精度并关闭融合运算。

GPU 内核实现时间推进、费用恢复、目标筛选与锁定、桥梁/建筑寻路、局部避让、移动、部署和首次攻击延迟、普通/范围弹道伤害、护盾无溢出、控制击退、冲锋和递增伤害、皇家塔激活与伤害累计。寻路缓存以起止格及当前障碍形状为依据；死亡建筑不继续阻挡路线。

3.16.0 补齐动态召唤、死亡召唤、召唤物的出场脉冲、圣水生成与死亡回费、冲刺准备/飞行/落地/中断及飞行免伤、反伤、克隆单位与其死亡子单位、狂暴、减速、拉扯、地震、波次/持续/最高生命值法术、线形弹道和延迟/连续召唤法术。CPU/GPU 保留相同队列顺序、目标并列排序、每步单位行动快照和 96 个单位的参考模拟限制；CUDA 物理缓冲另留空间容纳该限制附近的一组召唤。

条件式两卡组合的延迟、首牌推进、敌方回应后的后续牌、第二次回应和剩余战斗均在 GPU 推进，按不同场景与后续落点批量执行。CPU 仍负责生成合法动作、选择敌方回应、战术目标与分数归并、预算管理、模型准入及最终出牌检查。保留 CPU 参考模拟器用于一致性对照和无 CUDA 回退；不存在“只为提高方案数而省略特殊机制”的路径。

尚未在参考模拟器实现的主动技能、变体及缺失属性仍沿用原来的明确不确定性，不因迁移而自动补齐。未来未知效果、超过 GPU 实体/弹道/效果容量、依赖或内核故障会报告或回退；超时不当作完成结果。

3.15.8 已接入死亡伤害及延迟、对塔倍率和空地限制、连锁逐跳目标与累计弹道时间、多目标/单目标重复弹道。3.16.0 的电法出场脉冲也在 GPU 执行。启动预热运行有单位且需要寻路的完整批次，避免只预热空状态。

无出牌候选时，日志显示当前圣水、可规划手牌数及最低费用，区分“无可支付牌”与“搜索未完成”。`compute.gpu_fallback_reasons` 记录实际阻止 GPU 的机制及单位；不通过虚构落点、重复 WAIT 或忽略费用提高方案数。

后续组合批次默认最多 128 个战斗分支；首步按较小波次提交，使短预算也能先完成公平比较，敌情假设有三种时减少同批根动作数。各方案共用出牌前的延迟模拟；没有敌方回应的阶段合并推进。按状态实际需要缩小实体和效果传输缓冲，效果队列容量不足时原子重试完整容量。GPU 截止或容量超限的批次不会发布部分状态、不会计为完成方案。已完成的批次全部交给公平比较，不因第一轮每牌一个落点已完成而丢弃同批其他结果。

落点和时间轴预筛使用融合 CUDA 内核，在一个计算中完成距离、拉扯、皇家塔覆盖、兵种比较和时间轴伤害；保持双精度、原特征及逐敌军归并顺序。减少大量小运算调用与传输；失败时仍可使用原张量路径及 CPU 回退。`ranking_backend` 区分实际使用的融合内核、张量和 CPU 路径。

GPU 端维护跨批次的有界寻路缓存，按起止格、障碍形状和桥梁位置区分；避免每个候选、每个帧重复搜索相同路线。

## 设置与日志

`gpu_combat_batch_size=128`；CUDA 可用时无需同时启动 CPU 战斗工作进程，无 CUDA 时仍按 `combat_workers=8` 回退；`root_comparison_budget_fraction=0.85` 将更多现有预算用于不同落点的首步比较。默认 160 毫秒预算及原自适应防守预算保留；GPU 搜索为最后的选择检查留出最多 15 毫秒。

日志追加 `CUDA 完整精算 N / 特殊机制 CPU 回退 M`，完成组合时追加 `CUDA 条件式后续 N`。`compute.gpu_combat` 记录设备、可用状态、失败原因、内核调用、当前帧和累计完成根动作数、完成组合数、回退及超时；`scope=full_reference_combat` 描述代码覆盖范围，`compute.combat_device` 显示本帧真实使用路径。格点评分仍是预筛；首步比较数是已完成、参与公平比较的根动作数，包含 WAIT。识别画面显示的 YOLO FPS 是另一个指标。

## 验证与复现

`python -m unittest tests.test_gpu_combat tests.test_gpu_combat_full tests.test_gpu_placement -v` 验证 CPU/GPU 同场景的单位位置、目标、生命、护盾、攻击时序、圣水、塔损、待结算弹道/效果、召唤 UID、克隆/冲刺状态及不确定性，并比较完整根动作和防守/展开/反攻/准备四阶段的条件式组合；CUDA 不可用时相关测试明确跳过。覆盖 119 张当前可模拟卡牌、12 场混合特殊机制、48 个不同落点、分段推进、单位容量附近召唤和截止后状态保护。

`python tools/benchmark_planner.py --samples 12 --budget-ms 160 --gpu-combat --gpu-batch 128` 只进行离线推演，不连接模拟器或出牌。`--no-gpu-combat --workers 8` 可比较同版本 CPU 路径。报告保存在被忽略的 `reports/planner-speed/throughput.json`；原始数据、模型和本地性能报告不上传代码仓库。具体性能随单位数量、机制、显卡负载及 CPU 负载变化，不能保证每帧都完成相同数量。

3.15.7 的历史测试曾得到 509 / 165 个完整首步比较，其中也包含 CPU 寻路及预算分配优化；这不是完整机制后端的当前保证。3.16.0 完整迁移后，本机每场景预热 2 次、采样 8 次，6 秒战斗范围和 160 毫秒预算下，已知敌情为中位 349（285–349），三种敌情假设为中位 117（57–117），这些场景实际 CPU 回退为零。结果受负载与场景影响，不是每帧方案数或实战胜率承诺。

CuPy 与 CUDA 编译依赖通过原共享系统用户 Python 环境安装；CUDA 内核缓存也在用户目录复用。打包包含战斗/落点 CUDA 源码和机制头文件，源码与 EXE 的代码身份均包含这些文件，避免只改 GPU 规则却仍被当作同一代码。旧 EXE 需重新构建才包含新代码和内核，BAT 启动直接使用当前源代码。
