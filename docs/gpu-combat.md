# GPU 批量战斗推演（3.15.7 / P2）

P2 是已实现的实验阶段，不代表真实对局验收或胜率提升。预测规则配置与训练模型版本仍单独显示。

## 实际计算路径

默认 `prediction.gpu_combat=true`，启动时在所选 CUDA 设备编译并预热战斗内核；无 CUDA、缺依赖或内核失败时保留原 CPU 模拟。每个 GPU 线程推进一个完整独立战斗分支，不同卡牌、不同落点与不同敌情假设并行。单个分支保留原模拟的单位行动和弹道结算顺序，使用双精度并关闭融合运算。

GPU 内核实现时间推进、费用恢复、目标筛选与锁定、桥梁/建筑寻路、局部避让、移动、部署和首次攻击延迟、普通/范围弹道伤害、护盾无溢出、控制击退、冲锋和递增伤害、皇家塔激活与伤害累计。寻路缓存以起止格及当前障碍形状为依据；死亡建筑不继续阻挡路线。

动态召唤、死亡召唤/伤害、资源生成、冲刺、反伤、连锁、多目标攻击、克隆与区域效果仍走原 CPU 完整模拟。含上述机制的初始场景整体回退；某张牌或敌方回应引入上述机制时，仅对应根动作回退。不会删减机制来凑方案数。敌方回应选取、战术评分、二卡组合精算及执行安全检查仍在 CPU。

每批默认最多 128 个战斗分支；敌情假设有三种时，自动减少同批根动作数。各方案共用出牌前的延迟模拟；没有敌方回应的阶段合并推进，减少状态传输。GPU 截止或容量超限的批次不会发布部分状态、不会计为完成方案。已完成的批次全部交给公平比较，不因第一轮每牌一个落点已完成而丢弃同批其他结果。

GPU 端维护跨批次的有界寻路缓存，按起止格、障碍形状和桥梁位置区分；避免每个候选、每个帧重复搜索相同路线。

## 设置与日志

`gpu_combat_batch_size=128`；`combat_workers=8` 为 CPU 特殊机制/后续精算提供工作进程；`root_comparison_budget_fraction=0.85` 将更多现有预算用于不同落点的首步比较。默认 160 毫秒预算及原自适应防守预算保留；GPU 搜索为最后的选择检查留出最多 15 毫秒。

日志追加 `CUDA 完整精算 N / 特殊机制 CPU 回退 M`。`compute.gpu_combat` 记录设备、可用状态、失败原因、内核调用、当前帧和累计完成根动作数、回退及超时；`compute.combat_device` 显示本帧真实使用路径。格点评分仍是预筛；首步比较数是已完成、参与公平比较的根动作数，包含 WAIT。识别画面显示的 YOLO FPS 是另一个指标。

## 验证与复现

`python -m unittest tests.test_gpu_combat -v` 验证 CPU/GPU 同场景的单位位置、目标、生命、护盾、攻击时序、圣水、塔损和待结算弹道，并比较完整根动作评分/敌方回应；CUDA 不可用时相关测试明确跳过。覆盖固定场景、48 个不同落点及目标锁定、分段推进、特殊机制回退和截止后状态保护。

`python tools/benchmark_planner.py --samples 12 --budget-ms 160 --gpu-combat --gpu-batch 128` 只进行离线推演，不连接模拟器或出牌。`--no-gpu-combat --workers 8` 可比较同版本 CPU 路径。报告保存在被忽略的 `reports/planner-speed/throughput.json`；原始数据、模型和本地性能报告不上传代码仓库。具体性能随单位数量、机制、显卡负载及 CPU 负载变化，不能保证每帧都完成相同数量。

本次离线对照每场景预热 2 次、采样 12 次，使用相同知识库、6 秒战斗范围和 160 毫秒预算。更新前的 4 进程方案，两组场景完整首步比较中位数均为 5；本更新 GPU 路径分别为 509（范围 125–509）与 165（81–165），实际耗时中位数约 155 / 148 毫秒。保留本更新其他优化、仅关闭 GPU 后，8 进程 CPU 对照为 481 / 117。整体提升包含搜索预算分配、主线程及寻路缓存优化，不能全部归因于 CUDA；不是实战胜率或每帧方案数承诺。

新增 CuPy 与 CUDA 编译依赖通过原共享系统用户 Python 环境安装；CUDA 内核缓存也在用户目录复用。旧 EXE 需重新构建才包含新代码和内核，BAT 启动直接使用当前源代码。
