# 3.2.0 · P1 预测推演（实验版）

本版实现独立预测决策引擎，原有 V5–M3 规则仍可选择。新增模块已经接入运行、日志与动作确认；当前平衡数据完整性、精确识别覆盖和对局收益尚未验收。

## 切换与运行

控制台停止后，在“版本”下拉框选择：

- **原有策略**：完全走原 BattlePolicy，“旧规则”下拉框继续选择 V5、M1、M2、M2.1、M3 的配置。
- **推演观察**：原策略执行，新引擎在同一观测上生成预测日志。不会把建议预留为动作。
- **P1 · 预测推演 · 实验版**：预测选择动作，经现有 ADB 和动作确认链执行；超时或必需数据缺失时回退原规则。

本机选择保存在 `.royal-lab.json`，两种选择互不覆盖，也保留其他本机设置。缺省没有新字段的旧配置仍使用原有策略。本仓库的 `config.json` 已选择 predictive；若本机已有显式选择，以本机选择为准。已运行的旧进程需要安全停止并重新启动。

命令行同样读取本机选择，可以仅覆盖本次：

```powershell
python -m crbot run --decision-engine predictive
python -m crbot run --decision-engine shadow
python -m crbot run --decision-engine legacy
python -m crbot knowledge audit
python -m crbot knowledge runtime-audit
```

## 实际决策过程

1. 在现有时序手牌与圣水观测上建立独立世界快照，不重复把同一帧计为两帧稳定识别。
2. 有战场识别模型时保留单位位置与牌名；没有精确牌名时，根据已有压路、群体与空地信息产生多组单位假设，日志显示 `lane_hypotheses`，不声称识别到了这些卡牌。
3. 维护敌方已见牌、实体跟踪、费用上下界及折扣后的费用估计。实体首次出现与确认部署是不同事件；同一兵连续出现、群体成员不会反复当成整张牌扣费。
4. 对可用手牌生成位置候选，并包含 WAIT。先对全部候选完成一层多假设计算，再在预算内细化敌方回应与我方下一步。每层只有全部候选比较完才生效，未完成的深层结果不替换完整浅层结果。
5. 空间模型推进移动、桥位、目标获取、首次攻击/攻击周期、投射物、群伤、护盾、建筑寿命、周期产兵、死亡伤害及分裂。还接入基本冲锋、递增伤害、眩晕和击退；不是游戏引擎的精确复刻。
6. 按双方塔伤、存活兵力、费用差和不利分支评分，只执行当前第一步。下一次观测重算。费用不足、过期、尚有待确认动作时不会额外点击。

3.2.0 默认每张可用手牌最多 12 个空间候选（`positions_per_card`，范围 2–24），四张合计最多 48 个落点加等待，不再受旧 `candidate_limit=9` 截断。每个候选比较同样的 3 组敌方假设；基础预测窗口 8 秒，根据敌军无阻挡到塔时间最长扩展至 24 秒，默认搜索预算 350 ms。超时只采用所有可用手牌都已完成的均衡位置轮次，未完成的下一轮不参与选优；连一轮都未完成才回退。`hand_evaluations` 记录每张牌候选数、完成数、缺失原因、最佳位置、评分和最坏塔伤。`completed_depth` 区分第一层和双方后续响应层。实际响应还包括识别与 ADB 延迟。

敌方回应候选来自已见牌和明确配置的未知牌先验，并非读到了隐藏手牌。对于未知轮转，不断言某牌必不在手。搜索只使用已知我方手牌的剩余牌，不凭空补出尚未知的下一张。

## 知识库与覆盖

### 3.1.0 动态防守落点

兵种与建筑不再只使用四个或两个固定点。先在己方合法区域生成两格间距的候选网格，再按敌军预计接触点、部署延迟、攻击距离和存活公主塔加入连续偏移点；根据截击时间、目标类型、拉扯可能性、塔的覆盖火力和远程安全距离排序。3.1.0 曾将全手牌压缩为 9 个根方案；3.2.0 已移除这项截断，逐牌比较各自空间候选。不是对所有连续坐标进行穷举，也不保证数学全局最优。

公主塔只能攻击射程内的合法目标并保持原位；两座存活塔可以同时攻击覆盖区内的敌军。模拟记录 `own_tower_shots`、`own_tower_damage` 和 `imminent_tower_exposure`，对预测窗口结束后即将遭受的伤害及残血塔风险加罚。建筑与兵种落点避开现存建筑、公主塔和国王塔占地，保守限定己方半场；法术候选包含预计抵达位置与敌群中心。不会把新落点重新压回原来的左右路锚点。

12 个离线单威胁位置场景中，新候选集合的最佳模拟评分均不低于旧固定点；其中包含巨人、野猪骑士、气球的不同推进位置。完整策略搜索在该次本机测试约 136–168 ms，低于配置的 350 ms。此结果仅为同一近似模拟器内的比较，不是实战胜率或设备响应耗时保证。无精确战场识别时仍使用明确记录的威胁假设；国王塔激活、完整碰撞和塔兵变体尚未实现。更新后重启预测引擎生效，原有策略和观察模式保留。

`data/cards.json` 继续供旧规则及图标匹配使用。新的 `data/battle_knowledge.json` 独立保存卡牌、单位、投射物、法术、状态效果、等级数组、变体资源和来源信息。

3.0.1 按用户指定的 [Clash Royale Deck Builder](https://www.clashroyaledeckbuilder.net/zh/clash-royale-cards) 导入全部 **121 张目录卡牌、1083 条等级记录**，补齐 12 张基础卡图；保留 11 张旧条目，合计 **132 张牌、132 张基础卡图、59 条变体资源记录**。目录及详情页面脚本的地址、获取时间和 SHA-256 随数据保存。目录自报核对日期为 2026-05-18，不能据此认定数值已通过当前平衡核验。

分等级生命值、伤害、DPS、范围伤害、护盾、死亡伤害和召唤物数值均保留在 `data/deckbuilder_cards.json` 和战斗知识库中，按明确等级编号读取，不按稀有度猜测数组位置。88 个已有单类单位条目接入详情数值，已支持法术接入伤害、半径和塔伤。混合部队不会把同一张表套给所有召唤物；未提供的字段保留带来源的历史机制。镜像的目录 0 费视为动态未知费用，不能免费出牌。

当前 **130 张有数值资料，119 张可进入近似模拟器**；镜像没有固定攻击数值，旧活动火箭仍缺数据。新卡详情入库不表示其特殊机制已实现：哥布林科学怪人等仍明确标记 `unmapped_combat_mechanics`，不能据此宣称全卡精确推演或对局验收。类型、标签和进化标记保留网站原值作为来源资料，已有人工策略、稳定 ID 与模型兼容标识不被覆盖。

### 3.2.0 效果记录及提前预测

`data/card_effects.json` 为全部 132 张牌逐卡保存单位效果、投射物、关联状态/区域效果、等级资料、来源和未完成项。运行 `python tools/build_card_effects.py` 重建；目录导入器也会同步生成。效果存在记录与完整可执行是两种状态。

新增可执行模式包含万箭齐发分波、雷电最高血量限目标、毒药持续伤害、滚木直线伤害、野蛮人滚桶直线后召唤、皇家速递延迟范围伤害后召唤、哥布林飞桶召唤、墓园逐次召唤、狂暴区域加速、克隆、飓风拉扯、地震建筑倍率。圣水收集器读取历史产水参数，狂战士读取详情普通攻击参数；冻结/眩晕可作用于塔。分波间隔、拉力、召唤散布和部分机制仍为近似，不能替代当前游戏规则核验。

仍未完整映射的 13 张：镜像、旧活动火箭、小王子、哥布林爆破手、哥布林机甲、可疑草丛、哥布林科学怪人、符文巨人、首领刺客、虚空、哥布林诅咒、灵体女皇、藤蔓。其他卡的英雄主动技能、变体和部分特殊效果也需单独验收。它们会在手牌比较中显示不可评估原因，不作为零效果方案；其他支持的手牌继续计算，不再整手回退。

敌军一旦被可靠观测，无论位于哪半场，都生成 `enemy_forecast`：预计目标、无阻挡到塔时间、观测移动速度。连续观测方向用于修正部署期间的预计接触点。出现单位不等于已确认敌方下牌；没有精确战场模型时仍只能基于威胁假设预测，不能声称已识别全部敌牌。合理等待也参与比较，预测不代表看见敌牌就必须立刻花费圣水。

离线重建：`python tools/import_deckbuilder.py`；重新获取目录和详情：`python tools/import_deckbuilder.py --refresh --icons`。导入器只解析静态字面量，不执行下载的脚本；卡数、重复 ID、数值或页面结构不符合预期时停止。重新运行历史 `build_battle_knowledge.py` 后，需再运行本导入器叠加详情数值。原有策略、推演观察和预测推演三个切换选项继续保留，阶段仍为 P1 实验版。

历史机制及详情未覆盖字段来自 [RoyaleAPI/cr-api-data](https://github.com/RoyaleAPI/cr-api-data/tree/d5461b0a59bff33c4da2fc845b07275b66b2d6ff/docs/json)，固定提交 `d5461b0a59bff33c4da2fc845b07275b66b2d6ff`（2023-10-18）。导入包保存原始字段、源文件 SHA-256、获取时间及 `historical_unvalidated` 状态，与详情页来源分开记录。不能把这些历史字段说成当前版本已核验数据。

`knowledge audit` 分别列出数值缺失、模拟不支持、部分机制未支持的卡牌。线性、多波和限目标等尚未处理的法术不强行当圆形群伤；必需手牌机制缺失时使用原策略。全卡目录始终保留，不用 0 填未知值。

更新或重建一个已选定的公开快照：

```powershell
python tools/build_battle_knowledge.py --revision d5461b0a59bff33c4da2fc845b07275b66b2d6ff
```

`--revision` 必须是完整提交 SHA；可以指定 `--catalog` 和 `--output` 生成候选包。导入不会修改旧卡牌目录。新知识版本由规范化内容计算，数据转换变化也会改变知识版本。更新卡库后需重启引擎，并重新检查覆盖和模拟场景。

## 预测的可信范围

- 本机没有战场模型时使用的是多种威胁假设，不是精确敌方出牌识别。无法由这个版本自动补出一个已经验证的全卡检测模型。
- 敌方费用、卡组、手牌与轮转是部分可观测信息。确认出牌事件可以收窄费用区间，但一般的单位出现不能证明支付了多少费用。
- 当前画面路径尚未读出双方塔血、单位血量与等级；默认按 11 级及不同存活假设计算。塔状态、速度换算、碰撞和位置变换都含近似。不能据此宣称精确伤害或胜率。
- 确认过的我方部署可形成短时存活假设，与检测到的实体分开保存；观测到同卡友军时避免重复增加同一批兵。确认失败不会增加部署事件。
- 进化、英雄能力、复制、复杂召唤/法术机制未全部覆盖。支持基础数值模拟与支持完整卡牌机制是不同指标。
- 推演本身在 CPU 执行；现有 GPU 手牌匹配路径保持。没有宣称搜索已使用 GPU。

因此，本版是可实际运行和切回的预测架构，并未完成“当前版本全卡精确推演”的最终验收。要达到该目标，还需要补齐并核验当前平衡参数/特殊机制，补齐场上识别及血量观测，并完成分层的受控对局对比。

## 状态、日志和模型隔离

启动输出软件版本、旧规则配置、所选决策引擎。每次决策的 `[推演]` 日志显示实际执行者、感知模式和建议/回退原因；每个动作还保留 `decision_engine`、知识版本、快照版本与有效期。

`runs/*/events.jsonl` 的 `battle_prediction` 包含候选动作、分项分数、敌方分支、后续动作、完整搜索层数及预算是否耗尽。WAIT 也记录原因。`.training-sync/runtime-status.json` 的 `prediction` 记录本次引擎状态；选择预测模式不保证每一手都由预测器执行。

3.4.0 及之前预测模式的回放身份为 `predictive_spatial_v1`，不冒用旧规则权重身份，不把模型同步视为质量通过。原有模式的保存键和兼容身份保留。原模式回退、观察模式执行、预测执行分别标记。旧模型不会因为新版本标签自动变成预测模型。

`knowledge runtime-audit` 汇总实际执行来源、回退原因、搜索耗时及确认的预测动作数。它不是胜率评估，不把回放中的另一种假设动作当成已经发生的真实结果。

## 3.2.1 快速防守与血量

默认 `prediction.fast_defense=true`、`budget_ms=100`：保留每牌最多 12 个动态位置，按手牌轮流比较。只完成当前敌军的第一层防守推演，不继续耗时搜索假设中的新增敌军与己方第二次出牌；新观测重新计算。身份不明仍保留两种场上单位假设。设置 `fast_defense=false` 可恢复多步分支搜索，原规则模式仍可切回。

比较不下牌与所有完成的防守候选，以最坏预计塔伤（含视野末端风险）为依据，在相差不超过 `defense_damage_tolerance=30` 的方案中优先省费。计算来不及完成公平比较时不发送旧规则补救点击，等待新画面。计划默认最多有效 0.5 秒，发送前仍执行过期检查。

精确单位检测框周围新增完整矩形血条读取，要求边框、连续填充、空余区一致且没有歧义；没有血条不视为死亡。仅支持清晰红/蓝血条，特效、遮挡或未加载精确检测模型时继续标记血量未知。血量允许下降及治疗回升，超过 0.6 秒未获得可靠新值就恢复未知；冷却和待确认期间也更新世界状态。检测能力尚需真实画面校准，合成血条测试不等同于实战验收。


## 3.2.2 出牌恢复

修复 3.2.1 的有效期回归：默认 `max_plan_age_s=2.5`，包含截图、识别和搜索耗时，发送前继续检查硬截止时间。此前 0.5 秒小于实际约 1 秒的截图及前置处理时间，导致每次新方案产生前就已过期。搜索预算仍为 100ms，并记录 `frame_age_before_perception_s` 便于定位设备延迟。超过总有效期仍不执行。

快速防守的省费选择只用于场上有敌军的情况。无有效敌军时回到原策略进行正常出牌，保留费用、手牌与动作确认检查；不再因所有候选塔伤同为零而永久等待。本次是日志定位及回归测试验证，实际对局恢复需重新启动更新后的机器人验证。


## 3.3.0 批量空间搜索

默认 `gpu_placement=true`、`compute_device=auto`，在初始化阶段预热 CUDA，使用一格网格批量计算位置×敌军×公主塔覆盖关系，最多考虑 24 个敌军。每张手牌候选上限从 12 提升为 24，战斗搜索预算从 100ms 提升为 160ms。CUDA 不可用时自动使用 NumPy 路径；两条路径保持同样的评分和网格。显式 `compute_device=cpu` 可用于对照。

GPU 负责几何拦截、拉扯和塔覆盖的候选排序；召唤、控制、伤害等详细战斗事件仍在 CPU 模拟，并非全战斗 GPU 推演。`plan.compute` 记录设备、实际调用数、评估位置数、错误及计算范围，首个 CUDA 排序调用输出日志。小批量 GPU 不保证比 CPU 更快，主要用途是扩大并行空间评估。

防守排序优先保住公主塔，然后最坏塔伤与视野末端风险，最后在默认 5 点差异以内省费；不再允许为了省费选择掉塔方案。未知兵种保留三种场上假设。最近实测日志仍全部为 `lane_hypotheses`，没有精确敌军身份输入，卡牌机制和血量也有未知项；增加算力不代表已获得精确最优防守或完成实战验收。


## 3.3.1 全部模型格点

默认 `all_placement_points=true`、`placement_grid_step=1.0`。基于当前 18×32 模型坐标域，按一格间距包含边界枚举，再逐点执行统一部署合法性检查。取消每牌候选数量限制以及相邻 1.5 格过滤；兵牌覆盖模型允许的半场区域，普通法术覆盖全场，皇家速递保留半场限制。不因附近暂时没有目标而删除法术格点。

示例局面：骑士、火枪手、加农炮各 268 个格点，火球 627 个，共 1431 个全部评分并进入候选集合。GPU 批量计算兵牌空间评分，法术使用现有效果近似评分。候选按各牌轮流进入详细战斗模拟，仍遵守 160ms 实时预算，不保证每点都完成详细推演。没有固定 24 个精算上限；完成多少由局面及耗时决定。

`hand_evaluations` 提供 `positions`、`spatial_scored`、`evaluated`；`compute` 提供 `grid_step_tiles`、`all_placement_points`、`spatial_scored`、`combat_evaluated`、`combat_complete`。控制台也区分全量评分和战斗精算覆盖率。全部评分不等于全部完成事件级战斗模拟，更不等于真实游戏的全局最优解。

合法域沿用当前保守地图模型：塔/建筑占位和己方半场等规则；敌塔被毁后的扩展部署区域及完整碰撞规则尚未实现。因此这里的“全部”指当前模型合法域中的每个格点，不是每一个屏幕像素，也不声称已精确还原所有游戏部署规则。原策略切换保留。


## 3.4.0 低延迟链路

默认开启 `automation.latest_frame_capture`：独立线程连续读取 ADB 原始帧，缓冲容量始终为 1；过时帧被覆盖，不排队逐张计算。记录采集开始/完成时间，动作有效期仍包含采集耗时。原始帧格式不受支持或传输失败时退回原 PNG 截图路径。退出、异常时停止采集线程。

确认阶段只接受在点击完成后开始采集的帧，并要求新的帧序号，避免旧帧或重复帧被用于动作确认。发送前如已有更新画面，复核所选手牌、可读费用和威胁是否消失；不满足条件时回滚预留动作并取消点击。没有新画面时保留原计划的过期检查。血条遮挡、身份未知时不能保证已确认每个敌人的生死。

牌槽像素和识别参数完全一致时复用匹配结果，任一变化立即失效；实际新帧的时序确认仍照常进行。`vision.card_match_prewarm` 把 CUDA 匹配库初始化移至启动阶段，`warmup_calls` 与 `gpu_match_calls` 分别统计，`unchanged_slot_cache_hits` 展示缓存命中。

`gpu_trajectory_screening` 在全格点排序中批量计算 33 个时间采样的 DPS、拉扯时间和预计塔伤，CPU/CUDA 使用相同公式。它是近似筛选模型，并非完整技能事件模拟：召唤、控制、碰撞与实际目标切换仍由原 CPU 模拟器作进一步检查。全格点覆盖不缩减，详细精算继续受实时预算限制。

运行状态新增 `capture`（后端、单帧耗时、帧龄、产帧数、固定容量、错误），响应统计增加 `pre_send_recheck`、`capture_to_send`。后者衡量从原决策帧开始采集到首次点击发起的时间，不能与单纯搜索耗时混为一谈。

本机只读测量：PNG 截图约 978ms，原始帧单次约 576ms，连续原始帧约 454–562ms；这些是截图传输测量，不是完整实战延迟。无新一轮实战验收，也仍缺少已验证的精确战场识别模型。


## 3.5.0 攻防与验证基础

地图通过 `prediction.arena_geometry` 统一转换屏幕与 18×32 格点。当前标定来自本机 540×960 对局参考图：河道位于画面高度约 42.7%，己方公主塔中心约 62.5%。原映射分别为 50% 和 77%，会让拉扯与塔覆盖预测偏离实际画面。此配置明确标记为待多场景验证；改变布局后必须重新核对，不代表自动完成任意画面标定。

`prediction.tower_bar_rois` 读取四座公主塔的连续红蓝血条。遮挡、缺失或不一致返回未知，不推断塔已被摧毁。尚未新增国王塔激活识别或敌塔倒下后的扩展部署域。单位观测按实际帧龄与测得速度做至多 0.75 秒的线性前推，未知速度不会被当作已知移动路线。

模拟器将部署等待、攻击冷却、首次攻击准备分开：攻击冷却不会冻结追击，首次攻击准备在进入射程后开始。已观察单位的真实攻击相位仍可能未知。现有卡牌条目继续标记近似或缺失，不能将通用计时修复等同于全部特殊机制准确实现。

`unified_tactics=true` 时，空场发展、反推与防守共享模拟器；发展和反推默认保留 3 费，高费等待有节奏代价。全部合法格点评分保持开启。在总预算内先公平比较手牌，再用剩余预算比较每张牌最佳根动作及等待的条件式后续：1.5 秒后从剩余手牌的已有位置候选中选择补牌，进攻分支加入敌方防守假设。只有整组比较完成才发布 `combo_candidates`；超时保留已完成的第一步比较。它不是全格点多步穷举，也不是全局最优证明。后续动作只用于评价，每次实际出牌仍需新画面、费用和确认检查。

新行为的预测回放身份为 `predictive_calibrated_v2`，避免与旧模拟策略数据自动混用；旧策略保存键及模式切换保留。版本仍显示 P1 实验阶段，不新增已验收阶段。

可运行：

```powershell
.venv\Scripts\python.exe -m crbot battle-lab prepare
.venv\Scripts\python.exe -m crbot battle-lab evaluate
```

`prepare` 在本机 `reports/battle_lab/` 生成逐卡机制状态、真实训练审计和待人工复核队列。使用现有 `annotate.bat` 标注源帧；自动筛选的疑难帧不是人工真值。`evaluate` 运行 30 个合成场景，仅检查合法性、费用与能否返回动作，不把这些检查当作策略收益验收。`runtime-audit` 新增后续同轨迹观测与线性预测的格点偏差；参考是后续检测结果，仍不是人工标注真值。

本轮审计发现 40,879 个采集帧，但人工帧、人工框与已标注卡牌均为零。没有已验证的精确战场模型可直接加载。训练、半格预测准确度、最优防守收益和真实端到端延迟验收仍需标注及真实对局；完整特殊机制和全战斗 GPU 事件模拟也未实现。现有 GPU 继续负责批量空间与近似轨迹评分。

本轮验证：307 项单元与集成测试通过；实际配置的 30 个合成场景全部返回合法可负担动作或等待，均完成条件式后续比较。该次 CUDA 场景运行的搜索中位数约 116ms、P95 约 118ms，仅衡量搜索，不包含截图、识别、ADB 点击或实战结果。


## 3.5.1 开局和结束状态修复

实际日志显示匹配大厅的紫色区域被误判为战斗费用条，约 4 秒后加载动画触发连续缺失判定；旧流程提前计数并清除战斗状态，真实战斗画面出现后无法恢复，最终结算超时。

开局现在同时要求 `battle_start_consecutive_frames=2` 和 `battle_start_stable_s=0.7`，不允许一次颜色命中直接开始。确认开局后立即运行出牌策略，`battle_start_grace_s=10` 仅保护结束判断，不是开场禁出牌时间。

费用条缺失达到 `battle_end_consecutive_frames=4` 且持续 `battle_end_absent_s=3` 秒，只记录 `battle_end_pending`。保持当前对局、策略和回放，不增加完成局数。连续恢复战斗画面后记录 `battle_resumed_after_ui_gap` 并继续同一局。只有明确的确定按钮或宝箱结算画面才确认完成；启动前已有的奖励界面仍能正常处理。长时间没有战斗画面或结算证据继续按原超时停止，但不会把这一局虚报为完成。

验证覆盖匹配闪帧、加载动画、高频检测、短局真实结算、界面恢复不重置策略，以及待确认后结算只计数一次；这些是状态机回归，不等同于新一轮实际对局验收。

## 并行推演（3.9.4）

`prediction.parallel_combat=true` 启用常驻 CPU 进程池；`combat_workers=4`、`combat_batch_size=4` 是当前默认。进程数按机器逻辑核心数限制，最多 8 个；少于两个可用工作进程时使用串行。设为 `false` 可恢复串行详细模拟。GPU 原有格点评分和轨迹筛选保持不变。

启动游戏前创建并预热全部工作进程。知识库在每个进程内只加载一次；同一批候选复用同一帧的初始假设状态。每次最多提交与进程数相同的批次，不把整张格点表排成长队。工作进程只计算，不执行设备操作。主进程按提交顺序收集结果，每个候选必须完成同样的假设集合，才进入原有公平比较与决策流程。第二层组合精算仍在主进程执行。

每批使用统一截止时间；过期任务协作退出，未开始的任务取消。旧帧仍在收尾时，新帧使用串行而不排在旧任务后面。工作进程不可用时记录原因，保留有效的完整比较结果或等待新画面，后续恢复串行。关闭机器人时回收工作进程，取消待执行任务。

运行状态 `prediction.plan.compute.parallel_combat` 显示配置进程数、实际返回结果的 `worker_pids`、预热进程、累计完整候选数、截止退出次数、错误及 `last_mode`。`deadline_exits` 包括在预算内完成部分公平比较后正常结束搜索，不等于本次无法下牌。`combat_device=cpu` 仍正确：这里是多个 CPU 进程，GPU 负责原有批量格点评分。只有日志和工作进程返回计数才证明并行实际使用，启用配置本身不是证明。

开发机受控测试中，相同 97 个候选、每候选三种假设，串行中位耗时 215–385 毫秒，四进程 79–143 毫秒；首轮串并行返回的各分支评分和顺序一致。在当前配置的规划入口（包含 GPU 评分、不含截图和设备出牌）中，五次测试的详细候选中位数：空场 64→271，防守 65→183，规划中位耗时约 126–136 毫秒。这些是该机器与测试场景的结果，不是所有设备的加速保证，也不代表真实胜率提升。

## 血量与两张牌组合（3.9.5）

默认 `unit_health_observation=true`。精确兵种框中的血量读取仍保留；另在战场区域寻找有边界的敌我血条，排除塔附近区域，支持粉色、青色及一定压缩误差。输出是血量比例而非绝对 HP。识别不清、遮挡、空血条和消失都保持未知，不把消失当死亡。血条对应的单位身体位置只是近似值；只有同阵营且空间关联唯一时才给已有单位附加血量，否则保留身份未知。未关联的血条也保留在诊断中。

`prediction.plan.visible_health_bars` 展示本帧可读血条；`unit_health` 展示各轨迹的阵营、兵种或未知身份、比例、观测时间及置信度。血量超过 0.6 秒不再当作新鲜读数。敌方和已识别友军的实际血量进入模拟；未知友军血量在不同情景中保守估计。只有身份明确、血量新鲜且至少 35% 的友军才可降低前排部署风险。身份未知的友军不会被赋予虚构的卡牌战斗能力，因此完整配合仍依赖兵种识别覆盖。

两张牌组合默认对每张牌的最佳首步和 WAIT 进行比较，`combo_root_positions` 可设 1–3。先模拟第一步与敌方回应，再根据存活单位、剩余血量和再生圣水，为剩余手牌重新生成后续落点，每牌默认 2 个（`combo_positions_per_card` 可设 1–4），并保留第二步 WAIT。与过去沿用首帧每张牌一个位置不同，第二步位置来自变化后的局面。组合考虑塔损、存活兵力、费用和预留圣水；只有完整比较所有选定首步后，才整体替代单步结果。组合有独立预算，并可在 CPU 进程池中按首步分工。预算不足保留完整的单步结果。

`compute.combination_search` 记录首步数量、后续位置数、是否完成和串／并行模式；分支保存 `followup_action`、预测 1.5 秒后的出牌时机、候选数及预计塔损。它不是强制连招：真实运行只执行第一步，之后重新观察和确认再决定第二步。首轮和组合各分配约一半规划预算。本节更新了 3.9.4 中组合仍在主进程计算的限制。

这是在候选集和有限时间内寻找更优收益，不是遍历任意张数、任意等待时长或所有连续落点的全局最优证明。护盾、不可见血条及缺少可靠身份的单位仍存在不确定性。单张真实记录中的可读血条及受控场景测试不能替代大规模标注集的准确率验证。


## 接近满费的等待修正（3.9.6）

防守费用优先以及每帧重新规划的条件式后续，都可能导致反复 WAIT。当前圣水至少 9.5、原选择为 WAIT 时，检查已完成首轮推演的立即出牌方案。只选择当前手牌中的可模拟部队，排除法术和建筑；出牌后保留 attack_reserve（默认 3）圣水。最坏塔损与迫近威胁不得超过立即等待和原条件计划两者中的较小值；部署暴露惩罚最多 0.25，模拟评分相对立即等待最多损失 3 分。合格方案先选低费，再按评分选择落点。

已经选择出牌时不覆盖原防守；未完成公平搜索或画面过期时仍不出牌。没有安全方案时允许等待，不保证零溢费。此规则处理眼前的资源利用，不代表实测胜率改善。compute.elixir_overflow 记录观测圣水、是否触发及保留等待的原因，便于后续区分策略等待和执行延迟。


## 敌方沉底备战（3.9.7）

统一推演增加 prepare 阶段：基于标定后的 32 格纵向坐标，所有存活敌方非塔单位位于 y<12（河道 y=16），可移动，按当前模拟速度到河道至少 4 秒，且双方单位尚未进入射程加 2 格的接触范围。任一敌军临桥、快速接近或已交战都保持 defend；该分类是当前观测与模拟数据下的估计。

prepare 不套用零费用优先的防守排序，首轮与串行/并行两牌分支均计算对方可能的应对。若原计划仍等待、场上尚无我方已建模部队且圣水至少 7，使用与满费修正相同的安全立即展开筛选，保留默认 3 圣水、预测塔损和暴露限制。已有友军时不重复触发提前展开护栏，但仍正常计算进攻配合和满费处理。compute.elixir_overflow 增加 preparation 和 threshold；仅在 prepare 触发时使用 safe_preparation 原因。未知友军身份可能影响是否已有部队的判断，不代表精确实战识别或胜率保证。


## 迫近塔的防守选择（3.9.8）

修复两牌组合完成后覆盖整个单牌候选集的问题：最终比较所有已完成单牌和完整组合，防守仍按最坏塔损、容差内费用排序。组合首步的每卡落点也按最坏塔损优先保留，避免总分高但保塔差的落点排除关键防守。

任一敌军的 unopposed_tower_eta_s 不超过 3 秒时，compute.urgent_tower_defense 为 true。首轮精算可使用完整规划预算，仍给学习修正保留原配置预算；组合只能利用剩余时间。此时最终选择排除以 WAIT 开头的组合，WAIT 只能使用不依赖后续出牌的单牌等待模拟结果，避免每帧延后防守。实际执行仍只下第一张牌，下一帧重算。

本轮使用日志中单牌保塔方案被组合排除、首轮约 80 毫秒超时的记录定位，并加入选择与预算回归。不承诺模型已识别全部敌军、零超时或零漏防；真实部署确认及画面过期检查继续生效。


## 圣水计量与首轮预算（3.10.1）

vision.elixir_meter_roi 是当前竖屏布局的圣水条独立标定区域 [0.268, 0.967, 0.972, 0.989]；旧 elixir_roi 保留为宽区域，不再用于配置了新区域的费用计算。决策、发送前复查及动作确认使用同一计量区域；未配置时兼容旧区域。布局改变需重新标定实际条带，不能把不含计量条的区域作为百分比分母。

在 runs/20260915_171428 的实际满费截图中，原读数约 8.54，新读数约 9.89；对应半费截图由 5.53 修正到 5.0。此项验证是已保存截图的离线读取，不等于新版本实战验收。

所有首轮精算都可用完整计划预算。只有完成各可用卡牌的公平位置比较且达到预算中点后，非紧急场景才提前结束首轮并尝试两牌组合；紧急场景继续优先首轮。完成前仍超出总预算则保持原过期与不完整结果保护，不能声称零超时。


## 展开意图与发送复查（3.10.2）

满费护栏或备战护栏产生的安全展开，携带 action_intent=overflow_development 或 preparation。发送前仍核对新鲜截图、原手牌和实际费用；对应圣水至少 9.5 或 7，否则取消。旧威胁消失不再取消这两类独立展开。普通防守和指向性行动保持 reactive 的威胁消失保护。

当前配置的出牌确认窗口为 2.2 秒。原始日志多次在已有首帧多信号证据后等不到第二帧；增加上限用于容纳截图延迟，仍要求两张独立新帧，达成即提前结束，不把未知结果自动改成确认。该改动不代表已经验证所有运行状态下均不溢费。


## GPU 手牌批处理（3.10.3）

日常 `UniversalHandRecognizer.recognize` 先提取同帧变化卡槽的 ORB 描述子，再合并上传至 CUDA。模板常驻显存，距离计算按最多 2048 个查询描述子分块，模板批量根据查询数和模板长度适配，距离及中间矩阵按约 64 MiB 预算计算（不代表整个进程显存上限）。结果按原卡槽边界在 GPU 上累加后统一下载；保持原 Hamming 比率判定、空卡槽处理及精确图像缓存。

`.training-sync/runtime-status.json` 的 `hand_matching` 新增 `gpu_matched_slots`、`gpu_template_batches`、`gpu_last_match_ms`、`gpu_last_batch_templates`。`gpu_match_calls` 现在统计合并提交次数，不能直接与旧版逐卡槽次数比较；预热不计入调用、卡槽和模板批次数。最近耗时包含匹配的数据传输与同步，不含 ORB 和截图耗时。无需修改启动方式，正常 BAT 启动继续使用现有 CUDA 环境准备；显式 CPU 和无 NVIDIA 机器保留 CPU 路径。

本机 RTX 5070 Ti Laptop GPU 的 191 模板、5 张保存的真实对局截图，每张 3 次、清空卡槽缓存的热运行对比中，整帧识别中位耗时从旧版 74.0 ms 降到 61.0 ms，约缩短 18%；全部结果与 CPU 一致。这是截图重放验证，并非更新后的在线对局验收，也不代表整个机器人提速 18%。ORB、截图、A* 寻路及完整战斗模拟仍有 CPU 工作，利用率受场景与其他应用影响；验收以结果一致性和延迟为准。


## GPU 扩展与提前防守（3.10.5）

- GPU 新增整片部署区域合法性筛选（每批最多 4096 点）、法术覆盖评分及空场展开评分。CPU/GPU 使用相同判定；CUDA 异常回退 CPU，运行状态记录 `domain_points`、`spell_positions`、`quiet_positions`。完整战斗事件与 A* 仍由 CPU 执行，不把预筛结果当作已完成战斗推演。
- 默认 `placement_grid_step=0.5`；防守 DPS 轨迹从 33 个采样点改为 65 个（0.125 秒间隔，8 秒范围）。本机保存的满费场景空间候选由 1080 增至 4208。空间评分覆盖不等于每个格点都经过完整战斗模拟，仍分别报告 `spatial_scored` 和 `combat_evaluated`。
- 活跃非塔实体超过 16 时，启用一格搜索，预算最多 240 ms；其他场景保持 160 ms。首轮必须完成手牌间公平比较，不能为预留组合时间而提前中断首轮。两牌组合在单牌层完成后竞争剩余预算；某个组合根动作的所有场景与后续比较算完即可保留，后面的超时不会抹掉它。`combination_search.complete` 与 `completed_roots` 区分全部和部分完成。
- 到塔预测沿桥和障碍路径计算，扣除攻击距离及单位/塔半径。观测的朝塔速度只能在标称速度至 1.5 倍范围内提前警报，避免噪声或暂时停顿延后防守。`defense_lead_s` 包含可用手牌的部署/首次攻击（或法术延迟）及配置的下牌传输时间；`intervention_slack_s` 用于提前进入紧急防守。它是基于知识库与观测的估计，不是保证拦截成功的时间。
- 单牌及两牌详细模拟在出牌前先推进 `defense_pipeline_s`（默认 0.35 秒），所有方案使用相同观察时点与终止时点；等待不会获得额外未来防守信用。该延迟目前是配置值，并非实时测量设备延迟。
- 修正未激活国王塔提供虚假协防火力、只攻击建筑单位被计入打兵火力、法术忽略护盾和敌塔伤害倍率的问题。选牌继续优先保塔、减少预测塔伤，再在足够安全的方案里比较总费用。赚费后继续使用已有安全展开与满费保护，不为花费圣水而允许额外塔伤。

敌方圣水保留区间估计，敌方手牌和未来轮转未被完整观测；本版不会声称识别出完整速猪牌序，也不模拟未观测到的确定下一张己方卡牌。当前可比较四张现有手牌和条件式两牌组合，仍需下一帧重新确认后续下牌。检测遗漏、错误单位身份、血量误差和知识库机制近似仍限制准确度，必须以新版本真实对局再验收。


3.10.5 同时修正建筑目标单位的行进锁定：尚未进入塔攻击范围且未开始攻击蓄力时，可转向视野内更近的非塔防守建筑；已经开始攻击塔时保留目标。此规则解决模拟中提前锁塔导致建筑无法拉扯的问题，仍是目标选择近似，需实战检验。有限候选模式的默认每牌落点数由 12 增至 16，防止移动预测改变排序后遗漏已验证有效的近塔防守点；全格点模式不使用此截断。


建筑拉扯预筛还会逐格检查：部署延迟后的敌军位置到建筑的边缘距离必须进入其视野，并且比原塔目标更近；不满足时不给予拉扯收益，CPU/GPU 使用同一条件。加入 0.35 秒下牌延迟的本机野猪控制场景中，较早位置连续三次选加农炮，模拟塔伤 0，对照等待 951；计算约 129–161 ms。更晚两个位置仍预测塔伤，不能把早期场景的零伤推断为实战无伤保证。


## 防守延迟链路（3.10.6）

默认 `automation.mumu_ipc_capture=true`：MuMu 自动连接使用本机安装目录自带的 `external_renderer_ipc.dll`，读取当前显示页原始 RGBA，翻转成正向 RGB。SDK 不存在、连接/截图失败时回退 ADB raw，再回退 PNG；错误在 `capture.ipc_error` 可见。自定义 ADB 模式直接使用 ADB，不把其他设备误当 MuMu。SDK DLL 不打包到仓库。接口约定参考 [MAA 的 MuMu 控制器](https://github.com/MaaAssistantArknights/MaaAssistantArknights/blob/dev/src/MaaCore/Controller/MumuExtras.cpp)，本机另验证了 MuMu 15 的安装路径、颜色和方向。

`timing.capture_interval_s=0.05` 是两次截图开始之间的目标周期，截图耗时包含在周期内。接口超过目标周期就立即继续，最新帧队列容量始终为 1，识别不会排队处理旧截图。`timing.battle_poll_interval_s=0` 取消战斗循环结尾原有的 0.7 秒等待；导航继续用 `poll_interval_s=0.7`。`prediction.wait_recheck_s=0.1` 缩短 WAIT 后重看时间，不改变已下牌的冷却、手牌稳定性、发送前复核和动作确认。

血条候选先批量找填充边缘，跳过无候选行，继续执行原来的完整边框和歧义检查；等级标记只在原本有效区域计算颜色，保留全尺寸零填充和原形态学边界。6 张实际截图新旧结果一致，测试中的血条检测中位约 60→42 ms，等级标记约 12→9 ms。这些是同输入微基准，不代表所有场景的准确率或耗时。

连续战斗采样、预测日志和运行状态写盘在动作处理后执行，保留样本原观察时间。动作提案记录、发送前复核和发送后的确认仍走原有流程。运行时 `capture` 提供 `target_interval_s`、`actual_interval_s`、`actual_fps`；帧率为最近两个截图起点间隔的倒数。响应计时补充 `foreground_check`、`battle_ui_checks`、`battle_cycle`，分别定位前台 ADB 查询、战斗入口 UI 检查以及观察到动作处理和采样结束的耗时，最后一个指标不包含随后的状态写盘。

本机只读实测：1080×1920 ADB raw 中位约 0.85 秒，PNG 约 1.56 秒，IPC 在实时链路约 0.03–0.05 秒；0.05 秒目标的短测观察到约 20 FPS。完整战斗识别与推演早期测试约 0.39–0.49 秒；后续画面发生变化，不能直接比较为同场景收益，也不能声称已经稳定 0.25 秒。前台检测、UI 检查、发送与确认还有额外成本。正在运行的旧进程不会热加载代码，需重启机器人后核对 backend 和整链路计时；本次只读测试没有发送实战点击，也不构成无伤防守验收。

## 可执行首轮与出牌优先（3.10.7）

实战日志发现：GPU 可以完成上千个格点的预评分，但旧版 CPU 工作进程按批次返回；批次没有完成就拿不到其中已经完成的首个动作。与此同时，全格点模式要求每张可用牌至少完成三处落点才发布比较，导致 160 ms 用完后只得到空结果。一次问题日志统计为 235 次推演中 174 次 timeout；它不是主动攒费。

首轮现在包含 WAIT 和每张可用手牌各一个落点，每个动作单独派发给持久工作进程。其结果按原顺序返回，继续保留相同的场景、预测时长和卡牌公平性。完成一整轮就保留可用比较，更多位置和两牌组合继续按预算细算。后续超时保留已完成的首轮，未比较完全部可用手牌时仍不伪装成完整结果。GPU 仍预评分全格点，完成首轮也不代表详细模拟了全部格点。`compute.usable_comparison` 和 `completed_fair_rounds` 明示区别，选择日志直接写出首步动作。

默认 `prediction.prefer_immediate_play=true`：在已经完成的方案中，优先保留当前手牌、当前圣水可支付且落点合法的实际出牌方案，再用现有的塔损、费用和评分规则选出首步；WAIT 继续作为推演对照，但有可执行方案时不参加最终出牌选择。该开关会牺牲部分主动攒费机会，属于用户选择的积极执行策略，不承诺收益总是优于等待。没有可用方案时如实记录 `no_completed_legal_play`，不伪造手牌或点击。

本机保存的问题快照只读复测：旧版连续五次 timeout；修复版第一次冷启动仍可能 timeout，之后四次均完成 WAIT 加四张手牌共五个方案，返回电精灵出牌方案，约 161 ms。此证据验证了之前丢弃首轮结果的问题，尚不是实际点击确认或胜率验收；高复杂度画面仍可能无法在单帧预算内完成首轮。

## 为下一次防守存费（3.10.8）

当前默认改为 `prefer_immediate_play=false`、`development_reserve_gate=true`。取消有合法方案就强制出牌，保留首轮单独返回、公平首轮结果保存和快速重新观察。WAIT 恢复参与收益比较，但不会因后续精算超时丢掉已经算完的有效比较。

费用检查针对每个候选分别进行：从四张已知手牌中排除本次将打出的槽位，在剩余牌里寻找可持续防守的组合，覆盖剩余手牌实际具备的对空和对地能力。使用卡牌当前配置等级的攻击目标、伤害、攻速、部队数量、血量和护盾；只打建筑的单位不视为守军，某层可攻击单位合计血量加护盾低于 300 时，不将其当作该层的持续防守保障。这是保守的能力筛选，不是对任意敌军的胜负证明。预留至少 `attack_reserve`（默认 3）费；组合需要 4、6 等更高费用时按更高值保留。

不假定下张抽到什么牌，也不提前把尚未恢复的圣水算入可用余额。剩余手牌本来没有某一层的应对时，`uncovered_layers` 如实标记，不虚构对空/对地能力。出牌后费用低于预留的方案被排除，除非**同一首步的已完成单牌模拟**相较立即等待，最坏塔损加迫近暴露减少超过 30（掉塔计大额损失）。紧急标签本身不允许随便透支；未来两牌组合的承诺也不能充当当前首步的救塔证据。

防溢出展开只检查经过预留筛选的首步，不得把排除掉的花费方案重新加回。无合格展开时允许存费等待防守；极端高费手牌可能没有同时满足展开和后续留费的方案。诊断 `compute.development_reserve.options` 逐项记录出牌后费用、所需预留、保留的防守卡、缺失覆盖和是否因当前减塔损获准动用预留；WAIT 日志明确显示留费原因。

本机旧策略实战记录中，初次抽样有 13 次确认出牌时左右两路威胁值均为 0，其中 10 次出牌后不足 1 费。保存记录的离线费用规则重放中，86 个原 ready 决策有 70 个被新预留门槛排除，16 个具有当前首步减塔损证据。重放只验证新门槛会阻止原来的透支，不代表重新运行整场比赛后的出牌数、胜率或实战已经生效。

## 有界比较和完成结果回收（3.10.9）

默认 `decision_horizon_cap_s=6` 限制快速模式的本轮详细战斗模拟时长；到塔路线预测仍保留，但不再因为远处敌军而把每个候选的详细模拟自动拉长到 24 秒。同轮 WAIT、出牌和条件组合使用相同的实际模拟时长，不混合长短时长的评分。每帧继续用新观测滚动评估。该调整降低远期细节覆盖，不能将 6 秒内的评分当成整场收益。

首步并行计算使用完成顺序返回，父进程按原候选顺序整理已完成结果，避免选择由恰好返回先后来决定。到预算末尾先读取已完成任务；一个任务未算完不会阻止其他已完成任务被回收。仍限制在固定工作进程数内，不为新画面堆积旧任务；未完成的上一帧不会与当前帧混用。

默认 `allow_partial_comparison=true`：如果所有可用手牌的首轮未齐，但 WAIT 和至少一个出牌根动作已经完成全部假设分支，可以用这个完整子集继续选择。相同观察版本、场景和模拟时长是前提；没有 WAIT 基准或只有半个动作的场景结果时，仍不执行。`partial_hand_comparison` 记录已比较与缺失卡牌，并标记 `global_best_claimed=false`；`completed_fair_rounds=0` 不会被伪装成完整全手牌比较。部分结果仍走原有存费、塔损、合法性和发送前复核；缺失卡牌依然保留在手牌中，防守留费不会漏掉它们。

`compute.stage_ms` 新增建模/到塔预测、空间评分及首轮比较耗时；`decision_horizon` 分别记录请求与实际模拟秒数。它们用于定位剩余开销，不将 GPU 预评分数量当作已完成详细模拟。

本机固定 8 份历史超时快照（包含紧急防守）各测两次：修改前 9 timeout、4 wait、3 ready；修改后 0 timeout、13 wait、3 ready。多数收益是把原来没有结论的轮次变成经过费用/塔损检查的等待决定，而非强制增加出牌。该样本很小且来自同一运行记录，不代表新实战零超时；首轮连 WAIT 基准都未完成、模型错误、过期或发送前条件改变时仍可能不出牌。


### 3.10.10 皇家塔风险等待检查

所有阶段在最终选择 WAIT 时，使用同轮已完成且通过费用与留费检查的立即出牌方案，对照立即 WAIT 的最坏分支皇家塔损失（掉塔优先、实际模拟伤害及 imminent_tower_exposure）。可减少风险超过 tower_wait_minimum_mitigation（默认 30）时，选择接近最低塔损的低费有效防守（接近范围沿用 defense_damage_tolerance，当前配置为 5）。未来组合中的补牌不视为已执行防守；不增加模拟时长或额外搜索。沿用部署、接敌与管线延迟模型及有效减伤的留费豁免。日志 tower_wait_guard 记录是否改选、原因与预计减少的伤害及暴露；这些估值不是实际保证伤害。未形成完整比较仍不能据此强制出牌。


### 3.10.11 高危应急防守

当最终仍为 WAIT 且立即等待的最大塔伤及暴露达到 tower_emergency_damage（默认 600），重新检查本轮完整单步方案，绕过常态留费条件，但保留可支付、手牌、合法部署和交战能力检查。按照最坏塔损、平均塔损、费用、评分排序；最坏身份假设都失败时，仍可为其他可信假设出牌。即使全部场景未证明减伤，也执行可交战的最佳可用应急方案；不声称此举保证减伤。未知身份的交战能力考虑当前轨迹的所有已有假设，不能只按最坏的气球假设过滤地面防守。无可支付合法交战方案或没有完整比较时仍无法保证出牌。tower_emergency_defense 单独记录留费豁免、风险和分支改善情况。

## 3.12.8 计划到发送的时效修复

当日志反复出现 `status=rejected error=plan_expired` 时，表示未发送点击，不能算作成功出牌。3.12.8 在导航识别结束后选取最新截图，并重新检查战斗特征、结算按钮和宝箱页面；遇到页面切换就返回导航处理，不继续使用旧战斗画面。

计划时效检查完整计入路由前的感知耗时。优先复用后台已经处理的同帧手牌和标志；发送前识别出的手牌和圣水只用于同一张复查图，不重复识别。最终道路威胁检查使用当前标志和运动证据，不重复运行完整 YOLO，也不把尚未发送的落点当成己方单位屏蔽。动作提议先记录无图事件，前置截图在确认完成后以 `battle_action_pre_send_frame` 保存并关联同一 action_id，人工复核仍可读取前后截图。日志新增 `pre_send_recheck_s`，计划记录新增 `pre_decision_s`。

保持原有计划最大年龄和确认标准；过期计划继续拒绝，并在下一张新图采用受限搜索/已有的近塔应急估算。恢复搜索最多使用 600 毫秒，并扣除观测已有延迟、预留 500 毫秒给后续检查与发送，避免少量候选仍因固定的 160 毫秒预算连续失败。此修复不把估算标为完整推演，也不把试运行或拒绝记为成功。

默认配置关闭 `automation.continuous_perception`。此选项同时控制后台手牌/等级标记预处理与连续格点跟踪；关闭后仍使用最新帧采集和每次决策的前台识别，但格点显示不再额外逐帧跟踪。实机排查发现后台处理可使前台感知超过计划有效期。2026-09-16 使用 3.12.8 可执行程序及该配置完成一局离线人机验证：7 次发送、7 次 confirmed；该单局仅证明出牌链路恢复，不代表胜率或模型准确率验收。现有目录启动会读取目录中的 config.json；仅复制旧内置配置的可执行文件到新目录时，需要同时携带本次 config.json。
