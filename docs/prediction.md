# 3.2.0 · P1 预测推演（实验版）

本版实现独立预测决策引擎，原有 V5–M3 规则仍可选择。新增模块已经接入运行、日志与动作确认；当前平衡数据完整性、精确识别覆盖和对局收益尚未验收。

## 切换与运行

控制台停止后，在“版本”下拉框选择：

- **原有策略**：完全走原 BattlePolicy，“旧规则”下拉框继续选择 V5、M1、M2、M2.1、M3 的配置。
- **推演观察**：原策略执行，新引擎在同一观测上生成预测日志。不会把建议预留为动作。
- **P1 · 预测推演 · 实验版**：预测选择动作，经现有 ADB 和动作确认链执行；超时或必需数据缺失时回退原规则。

本机选择保存在 `.royal-lab.json`，两种选择互不覆盖，也保留其他本机设置。缺省没有新字段的旧配置仍使用原有策略。本仓库的 `config.json` 已选择 predictive；若本机已有显式选择，以本机选择为准。已运行的旧进程需要安全停止并重新启动。

命令行同样读取本机选择，可以仅覆盖本次：

```powershell
python -m crbot run --decision-engine predictive
python -m crbot run --decision-engine shadow
python -m crbot run --decision-engine legacy
python -m crbot knowledge audit
python -m crbot knowledge runtime-audit
```

## 实际决策过程

1. 在现有时序手牌与圣水观测上建立独立世界快照，不重复把同一帧计为两帧稳定识别。
2. 有战场识别模型时保留单位位置与牌名；没有精确牌名时，根据已有压路、群体与空地信息产生多组单位假设，日志显示 `lane_hypotheses`，不声称识别到了这些卡牌。
3. 维护敌方已见牌、实体跟踪、费用上下界及折扣后的费用估计。实体首次出现与确认部署是不同事件；同一兵连续出现、群体成员不会反复当成整张牌扣费。
4. 对可用手牌生成位置候选，并包含 WAIT。先对全部候选完成一层多假设计算，再在预算内细化敌方回应与我方下一步。每层只有全部候选比较完才生效，未完成的深层结果不替换完整浅层结果。
5. 空间模型推进移动、桥位、目标获取、首次攻击/攻击周期、投射物、群伤、护盾、建筑寿命、周期产兵、死亡伤害及分裂。还接入基本冲锋、递增伤害、眩晕和击退；不是游戏引擎的精确复刻。
6. 按双方塔伤、存活兵力、费用差和不利分支评分，只执行当前第一步。下一次观测重算。费用不足、过期、尚有待确认动作时不会额外点击。

3.2.0 默认每张可用手牌最多 12 个空间候选（`positions_per_card`，范围 2–24），四张合计最多 48 个落点加等待，不再受旧 `candidate_limit=9` 截断。每个候选比较同样的 3 组敌方假设；基础预测窗口 8 秒，根据敌军无阻挡到塔时间最长扩展至 24 秒，默认搜索预算 350 ms。超时只采用所有可用手牌都已完成的均衡位置轮次，未完成的下一轮不参与选优；连一轮都未完成才回退。`hand_evaluations` 记录每张牌候选数、完成数、缺失原因、最佳位置、评分和最坏塔伤。`completed_depth` 区分第一层和双方后续响应层。实际响应还包括识别与 ADB 延迟。

敌方回应候选来自已见牌和明确配置的未知牌先验，并非读到了隐藏手牌。对于未知轮转，不断言某牌必不在手。搜索只使用已知我方手牌的剩余牌，不凭空补出尚未知的下一张。

## 知识库与覆盖

### 3.1.0 动态防守落点

兵种与建筑不再只使用四个或两个固定点。先在己方合法区域生成两格间距的候选网格，再按敌军预计接触点、部署延迟、攻击距离和存活公主塔加入连续偏移点；根据截击时间、目标类型、拉扯可能性、塔的覆盖火力和远程安全距离排序。3.1.0 曾将全手牌压缩为 9 个根方案；3.2.0 已移除这项截断，逐牌比较各自空间候选。不是对所有连续坐标进行穷举，也不保证数学全局最优。

公主塔只能攻击射程内的合法目标并保持原位；两座存活塔可以同时攻击覆盖区内的敌军。模拟记录 `own_tower_shots`、`own_tower_damage` 和 `imminent_tower_exposure`，对预测窗口结束后即将遭受的伤害及残血塔风险加罚。建筑与兵种落点避开现存建筑、公主塔和国王塔占地，保守限定己方半场；法术候选包含预计抵达位置与敌群中心。不会把新落点重新压回原来的左右路锚点。

12 个离线单威胁位置场景中，新候选集合的最佳模拟评分均不低于旧固定点；其中包含巨人、野猪骑士、气球的不同推进位置。完整策略搜索在该次本机测试约 136–168 ms，低于配置的 350 ms。此结果仅为同一近似模拟器内的比较，不是实战胜率或设备响应耗时保证。无精确战场识别时仍使用明确记录的威胁假设；国王塔激活、完整碰撞和塔兵变体尚未实现。更新后重启预测引擎生效，原有策略和观察模式保留。

`data/cards.json` 继续供旧规则及图标匹配使用。新的 `data/battle_knowledge.json` 独立保存卡牌、单位、投射物、法术、状态效果、等级数组、变体资源和来源信息。

3.0.1 按用户指定的 [Clash Royale Deck Builder](https://www.clashroyaledeckbuilder.net/zh/clash-royale-cards) 导入全部 **121 张目录卡牌、1083 条等级记录**，补齐 12 张基础卡图；保留 11 张旧条目，合计 **132 张牌、132 张基础卡图、59 条变体资源记录**。目录及详情页面脚本的地址、获取时间和 SHA-256 随数据保存。目录自报核对日期为 2026-05-18，不能据此认定数值已通过当前平衡核验。

分等级生命值、伤害、DPS、范围伤害、护盾、死亡伤害和召唤物数值均保留在 `data/deckbuilder_cards.json` 和战斗知识库中，按明确等级编号读取，不按稀有度猜测数组位置。88 个已有单类单位条目接入详情数值，已支持法术接入伤害、半径和塔伤。混合部队不会把同一张表套给所有召唤物；未提供的字段保留带来源的历史机制。镜像的目录 0 费视为动态未知费用，不能免费出牌。

当前 **130 张有数值资料，119 张可进入近似模拟器**；镜像没有固定攻击数值，旧活动火箭仍缺数据。新卡详情入库不表示其特殊机制已实现：哥布林科学怪人等仍明确标记 `unmapped_combat_mechanics`，不能据此宣称全卡精确推演或对局验收。类型、标签和进化标记保留网站原值作为来源资料，已有人工策略、稳定 ID 与模型兼容标识不被覆盖。

### 3.2.0 效果记录及提前预测

`data/card_effects.json` 为全部 132 张牌逐卡保存单位效果、投射物、关联状态/区域效果、等级资料、来源和未完成项。运行 `python tools/build_card_effects.py` 重建；目录导入器也会同步生成。效果存在记录与完整可执行是两种状态。

新增可执行模式包含万箭齐发分波、雷电最高血量限目标、毒药持续伤害、滚木直线伤害、野蛮人滚桶直线后召唤、皇家速递延迟范围伤害后召唤、哥布林飞桶召唤、墓园逐次召唤、狂暴区域加速、克隆、飓风拉扯、地震建筑倍率。圣水收集器读取历史产水参数，狂战士读取详情普通攻击参数；冻结/眩晕可作用于塔。分波间隔、拉力、召唤散布和部分机制仍为近似，不能替代当前游戏规则核验。

仍未完整映射的 13 张：镜像、旧活动火箭、小王子、哥布林爆破手、哥布林机甲、可疑草丛、哥布林科学怪人、符文巨人、首领刺客、虚空、哥布林诅咒、灵体女皇、藤蔓。其他卡的英雄主动技能、变体和部分特殊效果也需单独验收。它们会在手牌比较中显示不可评估原因，不作为零效果方案；其他支持的手牌继续计算，不再整手回退。

敌军一旦被可靠观测，无论位于哪半场，都生成 `enemy_forecast`：预计目标、无阻挡到塔时间、观测移动速度。连续观测方向用于修正部署期间的预计接触点。出现单位不等于已确认敌方下牌；没有精确战场模型时仍只能基于威胁假设预测，不能声称已识别全部敌牌。合理等待也参与比较，预测不代表看见敌牌就必须立刻花费圣水。

离线重建：`python tools/import_deckbuilder.py`；重新获取目录和详情：`python tools/import_deckbuilder.py --refresh --icons`。导入器只解析静态字面量，不执行下载的脚本；卡数、重复 ID、数值或页面结构不符合预期时停止。重新运行历史 `build_battle_knowledge.py` 后，需再运行本导入器叠加详情数值。原有策略、推演观察和预测推演三个切换选项继续保留，阶段仍为 P1 实验版。

历史机制及详情未覆盖字段来自 [RoyaleAPI/cr-api-data](https://github.com/RoyaleAPI/cr-api-data/tree/d5461b0a59bff33c4da2fc845b07275b66b2d6ff/docs/json)，固定提交 `d5461b0a59bff33c4da2fc845b07275b66b2d6ff`（2023-10-18）。导入包保存原始字段、源文件 SHA-256、获取时间及 `historical_unvalidated` 状态，与详情页来源分开记录。不能把这些历史字段说成当前版本已核验数据。

`knowledge audit` 分别列出数值缺失、模拟不支持、部分机制未支持的卡牌。线性、多波和限目标等尚未处理的法术不强行当圆形群伤；必需手牌机制缺失时使用原策略。全卡目录始终保留，不用 0 填未知值。

更新或重建一个已选定的公开快照：

```powershell
python tools/build_battle_knowledge.py --revision d5461b0a59bff33c4da2fc845b07275b66b2d6ff
```

`--revision` 必须是完整提交 SHA；可以指定 `--catalog` 和 `--output` 生成候选包。导入不会修改旧卡牌目录。新知识版本由规范化内容计算，数据转换变化也会改变知识版本。更新卡库后需重启引擎，并重新检查覆盖和模拟场景。

## 预测的可信范围

- 本机没有战场模型时使用的是多种威胁假设，不是精确敌方出牌识别。无法由这个版本自动补出一个已经验证的全卡检测模型。
- 敌方费用、卡组、手牌与轮转是部分可观测信息。确认出牌事件可以收窄费用区间，但一般的单位出现不能证明支付了多少费用。
- 当前画面路径尚未读出双方塔血、单位血量与等级；默认按 11 级及不同存活假设计算。塔状态、速度换算、碰撞和位置变换都含近似。不能据此宣称精确伤害或胜率。
- 确认过的我方部署可形成短时存活假设，与检测到的实体分开保存；观测到同卡友军时避免重复增加同一批兵。确认失败不会增加部署事件。
- 进化、英雄能力、复制、复杂召唤/法术机制未全部覆盖。支持基础数值模拟与支持完整卡牌机制是不同指标。
- 推演本身在 CPU 执行；现有 GPU 手牌匹配路径保持。没有宣称搜索已使用 GPU。

因此，本版是可实际运行和切回的预测架构，并未完成“当前版本全卡精确推演”的最终验收。要达到该目标，还需要补齐并核验当前平衡参数/特殊机制，补齐场上识别及血量观测，并完成分层的受控对局对比。

## 状态、日志和模型隔离

启动输出软件版本、旧规则配置、所选决策引擎。每次决策的 `[推演]` 日志显示实际执行者、感知模式和建议/回退原因；每个动作还保留 `decision_engine`、知识版本、快照版本与有效期。

`runs/*/events.jsonl` 的 `battle_prediction` 包含候选动作、分项分数、敌方分支、后续动作、完整搜索层数及预算是否耗尽。WAIT 也记录原因。`.training-sync/runtime-status.json` 的 `prediction` 记录本次引擎状态；选择预测模式不保证每一手都由预测器执行。

3.4.0 及之前预测模式的回放身份为 `predictive_spatial_v1`，不冒用旧规则权重身份，不把模型同步视为质量通过。原有模式的保存键和兼容身份保留。原模式回退、观察模式执行、预测执行分别标记。旧模型不会因为新版本标签自动变成预测模型。

`knowledge runtime-audit` 汇总实际执行来源、回退原因、搜索耗时及确认的预测动作数。它不是胜率评估，不把回放中的另一种假设动作当成已经发生的真实结果。

相关测试覆盖：目录/等级/来源、缺失数据、实体去重与遮挡、动作幂等确认/回滚、费用与落点合法性、空地/建筑目标、护盾与分裂、敌方回应和后续动作、超时分层结果、旧模式兼容、设置无损保存，以及 1040×700 最小窗口下的选择器和控制按钮。

## 3.2.1 快速防守与血量

默认 `prediction.fast_defense=true`、`budget_ms=100`：保留每牌最多 12 个动态位置，按手牌轮流比较。只完成当前敌军的第一层防守推演，不继续耗时搜索假设中的新增敌军与己方第二次出牌；新观测重新计算。身份不明仍保留两种场上单位假设。设置 `fast_defense=false` 可恢复多步分支搜索，原规则模式仍可切回。

比较不下牌与所有完成的防守候选，以最坏预计塔伤（含视野末端风险）为依据，在相差不超过 `defense_damage_tolerance=30` 的方案中优先省费。计算来不及完成公平比较时不发送旧规则补救点击，等待新画面。计划默认最多有效 0.5 秒，发送前仍执行过期检查。

精确单位检测框周围新增完整矩形血条读取，要求边框、连续填充、空余区一致且没有歧义；没有血条不视为死亡。仅支持清晰红/蓝血条，特效、遮挡或未加载精确检测模型时继续标记血量未知。血量允许下降及治疗回升，超过 0.6 秒未获得可靠新值就恢复未知；冷却和待确认期间也更新世界状态。检测能力尚需真实画面校准，合成血条测试不等同于实战验收。


## 3.2.2 出牌恢复

修复 3.2.1 的有效期回归：默认 `max_plan_age_s=2.5`，包含截图、识别和搜索耗时，发送前继续检查硬截止时间。此前 0.5 秒小于实际约 1 秒的截图及前置处理时间，导致每次新方案产生前就已过期。搜索预算仍为 100ms，并记录 `frame_age_before_perception_s` 便于定位设备延迟。超过总有效期仍不执行。

快速防守的省费选择只用于场上有敌军的情况。无有效敌军时回到原策略进行正常出牌，保留费用、手牌与动作确认检查；不再因所有候选塔伤同为零而永久等待。本次是日志定位及回归测试验证，实际对局恢复需重新启动更新后的机器人验证。


## 3.3.0 批量空间搜索

默认 `gpu_placement=true`、`compute_device=auto`，在初始化阶段预热 CUDA，使用一格网格批量计算位置×敌军×公主塔覆盖关系，最多考虑 24 个敌军。每张手牌候选上限从 12 提升为 24，战斗搜索预算从 100ms 提升为 160ms。CUDA 不可用时自动使用 NumPy 路径；两条路径保持同样的评分和网格。显式 `compute_device=cpu` 可用于对照。

GPU 负责几何拦截、拉扯和塔覆盖的候选排序；召唤、控制、伤害等详细战斗事件仍在 CPU 模拟，并非全战斗 GPU 推演。`plan.compute` 记录设备、实际调用数、评估位置数、错误及计算范围，首个 CUDA 排序调用输出日志。小批量 GPU 不保证比 CPU 更快，主要用途是扩大并行空间评估。

防守排序优先保住公主塔，然后最坏塔伤与视野末端风险，最后在默认 5 点差异以内省费；不再允许为了省费选择掉塔方案。未知兵种保留三种场上假设。最近实测日志仍全部为 `lane_hypotheses`，没有精确敌军身份输入，卡牌机制和血量也有未知项；增加算力不代表已获得精确最优防守或完成实战验收。


## 3.3.1 全部模型格点

默认 `all_placement_points=true`、`placement_grid_step=1.0`。基于当前 18×32 模型坐标域，按一格间距包含边界枚举，再逐点执行统一部署合法性检查。取消每牌候选数量限制以及相邻 1.5 格过滤；兵牌覆盖模型允许的半场区域，普通法术覆盖全场，皇家速递保留半场限制。不因附近暂时没有目标而删除法术格点。

示例局面：骑士、火枪手、加农炮各 268 个格点，火球 627 个，共 1431 个全部评分并进入候选集合。GPU 批量计算兵牌空间评分，法术使用现有效果近似评分。候选按各牌轮流进入详细战斗模拟，仍遵守 160ms 实时预算，不保证每点都完成详细推演。没有固定 24 个精算上限；完成多少由局面及耗时决定。

`hand_evaluations` 提供 `positions`、`spatial_scored`、`evaluated`；`compute` 提供 `grid_step_tiles`、`all_placement_points`、`spatial_scored`、`combat_evaluated`、`combat_complete`。控制台也区分全量评分和战斗精算覆盖率。全部评分不等于全部完成事件级战斗模拟，更不等于真实游戏的全局最优解。

合法域沿用当前保守地图模型：塔/建筑占位和己方半场等规则；敌塔被毁后的扩展部署区域及完整碰撞规则尚未实现。因此这里的“全部”指当前模型合法域中的每个格点，不是每一个屏幕像素，也不声称已精确还原所有游戏部署规则。原策略切换保留。


## 3.4.0 低延迟链路

默认开启 `automation.latest_frame_capture`：独立线程连续读取 ADB 原始帧，缓冲容量始终为 1；过时帧被覆盖，不排队逐张计算。记录采集开始/完成时间，动作有效期仍包含采集耗时。原始帧格式不受支持或传输失败时退回原 PNG 截图路径。退出、异常时停止采集线程。

确认阶段只接受在点击完成后开始采集的帧，并要求新的帧序号，避免旧帧或重复帧被用于动作确认。发送前如已有更新画面，复核所选手牌、可读费用和威胁是否消失；不满足条件时回滚预留动作并取消点击。没有新画面时保留原计划的过期检查。血条遮挡、身份未知时不能保证已确认每个敌人的生死。

牌槽像素和识别参数完全一致时复用匹配结果，任一变化立即失效；实际新帧的时序确认仍照常进行。`vision.card_match_prewarm` 把 CUDA 匹配库初始化移至启动阶段，`warmup_calls` 与 `gpu_match_calls` 分别统计，`unchanged_slot_cache_hits` 展示缓存命中。

`gpu_trajectory_screening` 在全格点排序中批量计算 33 个时间采样的 DPS、拉扯时间和预计塔伤，CPU/CUDA 使用相同公式。它是近似筛选模型，并非完整技能事件模拟：召唤、控制、碰撞与实际目标切换仍由原 CPU 模拟器作进一步检查。全格点覆盖不缩减，详细精算继续受实时预算限制。

运行状态新增 `capture`（后端、单帧耗时、帧龄、产帧数、固定容量、错误），响应统计增加 `pre_send_recheck`、`capture_to_send`。后者衡量从原决策帧开始采集到首次点击发起的时间，不能与单纯搜索耗时混为一谈。

本机只读测量：PNG 截图约 978ms，原始帧单次约 576ms，连续原始帧约 454–562ms；这些是截图传输测量，不是完整实战延迟。无新一轮实战验收，也仍缺少已验证的精确战场识别模型。


## 3.5.0 攻防与验证基础

地图通过 `prediction.arena_geometry` 统一转换屏幕与 18×32 格点。当前标定来自本机 540×960 对局参考图：河道位于画面高度约 42.7%，己方公主塔中心约 62.5%。原映射分别为 50% 和 77%，会让拉扯与塔覆盖预测偏离实际画面。此配置明确标记为待多场景验证；改变布局后必须重新核对，不代表自动完成任意画面标定。

`prediction.tower_bar_rois` 读取四座公主塔的连续红蓝血条。遮挡、缺失或不一致返回未知，不推断塔已被摧毁。尚未新增国王塔激活识别或敌塔倒下后的扩展部署域。单位观测按实际帧龄与测得速度做至多 0.75 秒的线性前推，未知速度不会被当作已知移动路线。

模拟器将部署等待、攻击冷却、首次攻击准备分开：攻击冷却不会冻结追击，首次攻击准备在进入射程后开始。已观察单位的真实攻击相位仍可能未知。现有卡牌条目继续标记近似或缺失，不能将通用计时修复等同于全部特殊机制准确实现。

`unified_tactics=true` 时，空场发展、反推与防守共享模拟器；发展和反推默认保留 3 费，高费等待有节奏代价。全部合法格点评分保持开启。在总预算内先公平比较手牌，再用剩余预算比较每张牌最佳根动作及等待的条件式后续：1.5 秒后从剩余手牌的已有位置候选中选择补牌，进攻分支加入敌方防守假设。只有整组比较完成才发布 `combo_candidates`；超时保留已完成的第一步比较。它不是全格点多步穷举，也不是全局最优证明。后续动作只用于评价，每次实际出牌仍需新画面、费用和确认检查。

新行为的预测回放身份为 `predictive_calibrated_v2`，避免与旧模拟策略数据自动混用；旧策略保存键及模式切换保留。版本仍显示 P1 实验阶段，不新增已验收阶段。

可运行：

```powershell
.venv\Scripts\python.exe -m crbot battle-lab prepare
.venv\Scripts\python.exe -m crbot battle-lab evaluate
```

`prepare` 在本机 `reports/battle_lab/` 生成逐卡机制状态、真实训练审计和待人工复核队列。使用现有 `annotate.bat` 标注源帧；自动筛选的疑难帧不是人工真值。`evaluate` 运行 30 个合成场景，仅检查合法性、费用与能否返回动作，不把这些检查当作策略收益验收。`runtime-audit` 新增后续同轨迹观测与线性预测的格点偏差；参考是后续检测结果，仍不是人工标注真值。

本轮审计发现 40,879 个采集帧，但人工帧、人工框与已标注卡牌均为零。没有已验证的精确战场模型可直接加载。训练、半格预测准确度、最优防守收益和真实端到端延迟验收仍需标注及真实对局；完整特殊机制和全战斗 GPU 事件模拟也未实现。现有 GPU 继续负责批量空间与近似轨迹评分。

本轮验证：307 项单元与集成测试通过；实际配置的 30 个合成场景全部返回合法可负担动作或等待，均完成条件式后续比较。该次 CUDA 场景运行的搜索中位数约 116ms、P95 约 118ms，仅衡量搜索，不包含截图、识别、ADB 点击或实战结果。
